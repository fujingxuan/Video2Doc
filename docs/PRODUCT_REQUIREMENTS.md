# Video2Doc 项目开发任务书

你将从零开始创建并实现一个名为 **Video2Doc** 的本地软件项目。

当前仓库是全新仓库，不会提供旧代码、旧脚本或已有项目结构。请自行创建完整仓库、开发环境、项目骨架、数据库、前端、后端、测试和文档。

不要把它理解成一个普通的视频摘要工具。Video2Doc 的目标是：

> 将视频或音频转换为完整、结构化、可追溯、可长期保存的 Obsidian Markdown 学习材料。

它主要用于大学课程、技术讲座、科研报告、B站教学视频、YouTube 教学视频等内容。

软件的主要价值是降低从视频中获取信息的时间成本，把线性的视频学习过程转换为可搜索、可阅读的文字材料。AI 不负责替用户理解、总结和提炼知识。

# 一、必须遵守的产品原则

优先级为：

```text
质量 > 成本 > 处理速度
```

系统必须尽量完整保留原视频中的信息。

AI 不得擅自执行以下操作：

* 总结内容；
* 概括内容；
* 凝练观点；
* 删除事实、论证、案例和技术细节；
* 改变讲者或作者的观点；
* 补充原视频中不存在的结论；
* 把原内容改写成 AI 自己的解释；
* 自动生成核心观点；
* 自动生成知识卡片；
* 自动生成思维导图；
* 自动生成学习笔记；
* 自动生成问答；
* 自动进行知识分类；
* 自动创建 Obsidian 双向链接。

AI 目前只允许执行以下轻度编辑操作：

* 删除“呃、嗯、那个、然后呢”等明显语气词；
* 修复标点；
* 修复错误断句；
* 合并被语音识别错误切开的句子；
* 在不改变原有论述逻辑的情况下进行必要的局部顺序调整；
* 根据原文自然分段；
* 添加描述性小标题；
* 整理 Markdown 排版；
* 将 OCR 中能够明确补充语音缺失的信息融合到正文中。

AI 添加的小标题必须尽量直接描述讲者正在讨论的主题，不能使用总结性、评价性或夸张性标题。

允许：

```text
Transformer 的基本结构
Self-Attention 机制
训练过程中的损失函数
```

禁止：

```text
Transformer 成功的核心秘密
这一理论为何彻底改变了人工智能
本节最值得记住的三大结论
```

# 二、软件形态

第一版采用：

```text
本地 Web 前端 + 本地后台服务
```

软件运行在用户自己的 Windows 电脑上。

第一版为：

* 单用户；
* 单机运行；
* Windows 优先；
* 不需要云端部署；
* 不需要用户账号；
* 不需要多用户权限系统；
* 不需要浏览器插件。

用户设备环境：

```text
CPU：Intel 9955HX
GPU：RTX 5070 Ti Laptop
显存：12GB
操作系统：Windows
```

用户已经配置 OneAPI。

包括 Ollama 在内的本地模型，也会由用户接入 OneAPI。因此 Video2Doc 不需要直接连接 Ollama。

Video2Doc 中所有需要通过 API 调用的模型，都统一通过 OneAPI 的 OpenAI 兼容接口调用。

API 配置不得硬编码。

使用环境变量或本地安全配置保存：

```text
ONEAPI_BASE_URL
ONEAPI_API_KEY
```

仓库中只能提交 `.env.example`，不能提交真实密钥。

# 三、技术架构要求

优先采用 Python 后端，因为项目需要使用：

* yt-dlp；
* FFmpeg；
* Python 音视频处理工具；
* ASR 工具；
* PaddleOCR 或其他本地 OCR 命令；
* OneAPI；
* 本地文件系统。

建议技术栈可以采用：

后端：

```text
Python
FastAPI
Pydantic
SQLAlchemy
Alembic
SQLite
```

前端：

```text
React
TypeScript
Vite
```

前端状态和请求管理可以选择稳定、维护良好的方案，但不要引入不必要的复杂框架。

前后端应明确分离。

不要将整个软件写在一个大型 Python 文件中。

不要将业务逻辑直接写入 API 路由。

建议至少划分：

```text
API 层
应用服务层
领域模型层
持久化层
Pipeline 执行层
外部工具适配层
文件存储层
```

所有外部能力都应通过适配器接口调用，例如：

```text
MediaDownloader
AudioExtractor
ASRProvider
OCRProvider
TextModelProvider
OutputWriter
```

即使第一版某些能力只有一种实现，也应避免把具体命令散落在业务代码中。

# 四、核心对象

软件至少需要以下核心对象。

## 1. Task

一个输入视频或音频对应一个独立任务。

每个任务包含：

* 输入来源；
* 来源类型；
* 任务标题；
* 当前状态；
* 当前处理阶段；
* 总进度；
* 创建时间；
* 开始时间；
* 完成时间；
* 错误信息；
* 数据目录；
* 最终 Markdown 路径；
* 创建任务时的完整配置快照。

## 2. Task Queue

用户可以一次输入多个视频、音频或 URL。

每一个输入生成一个独立 Task。

队列允许存在多个等待任务，但同一时间只能执行一个任务。

第一版固定：

```text
最大并行任务数 = 1
```

暂时不要开放并发数量设置。

队列需要支持：

* 等待；
* 处理中；
* 已完成；
* 失败；
* 已取消。

任务完成、失败或取消后，自动尝试执行下一个等待任务。

软件重启后：

* 等待任务应继续保留；
* 已完成任务应继续保留；
* 失败任务应继续保留；
* 上次异常中断的运行中任务不能直接标记为完成；
* 应将异常中断任务标记为“已中断”或“待恢复”，并允许用户重试。

不要让队列状态只存在于内存中。

## 3. Model

模型由用户手动添加。

不自动从 OneAPI 拉取模型列表。

添加一个模型时，只需要：

* 模型名称；
* 可用于哪些处理环节的核心标签；
* 可选备注；
* 是否启用。

模型名称同时作为调用 OneAPI 时使用的模型 ID。

核心能力标签采用固定列表：

```text
ASR
OCR
TEXT_PROCESSING
VISION
```

第一版实际需要使用：

```text
ASR
OCR
TEXT_PROCESSING
```

一个模型可以拥有多个标签。

例如：

```text
模型名：gpt-5-mini
标签：TEXT_PROCESSING

模型名：whisper-large-v3
标签：ASR

模型名：paddleocr
标签：OCR
```

不要要求用户填写供应商、厂商或底层模型来源。

所有模型在 Video2Doc 看来都来自统一的 OneAPI 模型池。

## 4. Processing Profile

界面中可以称为：

```text
处理方案
模型组
工作流预设
```

内部建议统一命名为 `ProcessingProfile`。

ProcessingProfile 不是只保存模型名称，而是保存一整套可复用的处理配置，包括：

* ASR 模型；
* 是否启用 OCR；
* OCR 模型；
* 文本处理模型；
* 是否删除语气词；
* 是否修复断句；
* 是否自动分段；
* 是否生成小标题；
* 是否保留时间戳；
* 是否保留原始转写；
* 是否保留下载媒体；
* OCR 抽帧参数；
* Markdown 模板；
* Obsidian 输出目录；
* 数据资料目录。

内置预设可以包括：

```text
高质量模式
本地模式
快速模式
```

由于本地模型也统一经过 OneAPI，所谓“本地模式”只是用户自己配置的一组模型，不需要 Video2Doc 识别模型实际运行位置。

用户还可以创建自定义模型组。

用户选择一个模型组后，可以临时修改本次任务的配置。

临时修改只影响当前任务，不自动覆盖原模型组。

## 5. App Settings

至少保存：

* OneAPI Base URL；
* OneAPI API Key 的安全引用或本地配置；
* Obsidian Vault 路径；
* Video2Doc Inbox 路径；
* Video2Doc 数据资料目录；
* 上一次使用的 ProcessingProfile；
* 上一次任务的完整配置；
* 默认 Markdown 模板；
* 默认是否启用 OCR；
* 默认是否保留原始转写；
* 默认是否保留时间戳；
* 默认是否保留下载的视频；
* 默认是否保留中间抽帧。

每次新建任务时，自动加载上一次实际使用的设置。

不是每次强迫用户重新选择预设。

每个任务创建时必须保存配置快照。之后即使全局设置或模型组发生变化，也不能改变历史任务的配置记录。

# 五、输入方式

第一版支持两类输入。

## 1. URL

支持用户粘贴一个或多个 URL。

目标来源包括：

* B站；
* YouTube；
* 普通视频网页；
* 可直接访问的音视频 URL。

可以使用 yt-dlp 获取媒体和元数据。

每个 URL 生成一个独立任务。

需要保存：

* 用户输入的原始 URL；
* 实际获取媒体的地址，如能够获得；
* 平台；
* 视频标题；
* 作者或讲者；
* 频道或发布者；
* 发布时间；
* 视频时长；
* 视频简介；
* 原始语言，如能够识别；
* 缩略图，如能够获取。

如果 URL 无法解析，需要给出明确错误信息，不能只显示“处理失败”。

## 2. 本地文件

支持拖放或文件选择。

至少支持：

```text
MP4
MKV
MOV
WebM
MP3
M4A
WAV
```

也应允许 FFmpeg 能处理的其他常见音视频格式。

用户可以一次拖入多个文件。

每个文件生成独立任务。

第一版暂时不需要：

* 文件夹监听；
* 浏览器插件；
* 自动监听下载目录；
* 整个播放列表批量导入的复杂管理；
* 多层文件夹递归导入。

# 六、新建任务交互

首页或新建任务页面应包含：

* URL 输入框；
* 添加 URL 按钮；
* 本地文件拖放区域；
* 选择本地文件按钮；
* 当前准备添加的输入列表；
* 删除某个输入；
* 清空输入；
* 处理方案选择；
* OCR 开关；
* 高级设置；
* 加入队列按钮。

用户一次加入多个输入时：

* 每个输入创建一个任务；
* 默认使用相同的当前配置；
* 每个任务保存独立配置快照；
* 加入队列后，队列一次只处理一个任务。

任务加入队列前不要求用户逐个进入复杂确认页面。

但应尽量显示已知信息，例如：

```text
本地文件名
URL
输入类型
是否启用 OCR
所选处理方案
```

URL 的完整元数据可以在任务执行的媒体获取阶段再解析。

# 七、处理流水线

Pipeline 必须由独立、可记录、可失败、可重试的 Stage 组成。

建议阶段枚举：

```text
QUEUED
PREPARING
FETCHING_METADATA
DOWNLOADING_MEDIA
EXTRACTING_AUDIO
RUNNING_ASR
CLEANING_ASR
EXTRACTING_FRAMES
RUNNING_OCR
CLEANING_OCR
FUSING_CONTENT
WRITING_MARKDOWN
COPYING_OUTPUT
COMPLETED
FAILED
CANCELLED
INTERRUPTED
```

Pipeline 不得依赖只存在于内存中的中间状态。

每个阶段成功后应：

* 保存产物；
* 更新数据库；
* 更新任务状态；
* 写入阶段日志；
* 记录开始和结束时间。

阶段失败时应：

* 保存错误类型；
* 保存简洁的用户可读错误；
* 保存详细开发日志；
* 不删除已经完成的前序阶段产物；
* 允许从合理的阶段重新执行。

# 八、无 OCR 时的流程

当 OCR 关闭时：

```text
输入
→ 获取媒体信息
→ 下载或读取媒体
→ 提取音频
→ ASR
→ 保存原始 ASR 结果
→ AI 清洗 ASR
→ 分段
→ 添加描述性小标题
→ Markdown 格式化
→ 保存最终 Markdown
→ 复制或写入 Obsidian Inbox
```

文本处理模型负责：

* 清洗 ASR；
* 分段；
* 小标题；
* 最终 Markdown 格式整理。

不要为小标题或 Markdown 格式单独选择不同模型。

所有文本处理环节共用一个文本处理模型。

---

# 九、启用 OCR 时的流程

当 OCR 开启时，音频和画面形成两条数据分支。

## 音频分支

```text
提取音频
→ ASR
→ 保存 ASR 原始结果
→ AI 清洗 ASR
→ 保存清洗后的 ASR 文本
```

## 画面分支

```text
按配置抽取视频帧
→ OCR
→ 保存 OCR 原始结果
→ OCR 初步去重
→ AI 清洗 OCR
→ 保存清洗后的 OCR 文本
```

## 融合阶段

输入：

```text
清洗后的 ASR
+
清洗后的 OCR
```

融合模型仍使用同一个文本处理模型。

融合必须遵守：

1. 先完整阅读 ASR 清洗文本。
2. ASR 是最终正文的主要信息来源和叙述主线。
3. 再阅读 OCR 清洗文本。
4. OCR 只用于寻找 ASR 中明确缺失的信息。
5. 只补充能够从 OCR 内容中明确确认的信息。
6. 避免重复。
7. OCR 中与讲解无关的界面文字、平台按钮、字幕水印、广告、频道宣传、播放器文字不能进入正文。
8. OCR 中已经被 ASR 完整表达的内容不能再次加入。
9. 不得因为 OCR 中出现某个术语，就自行扩写相关知识。
10. 不得根据模糊 OCR 猜测公式、数字或术语。
11. 无法可靠判断的 OCR 内容应留在原始 OCR 文件中，不进入正文。
12. 融合完成后，在同一次文本处理阶段完成分段、描述性小标题和 Markdown 格式整理。

例如：

ASR 内容：

```text
这里的公式如图所示。
```

OCR 内容：

```text
Attention(Q,K,V)=softmax(QK^T/sqrt(d_k))V
```

可以把公式补入正文。

但如果 ASR 已经完整说出某个句子，OCR 又识别到幻灯片上的相同句子，则不能重复添加。

# 十、AI 文本处理要求

建议为不同文本处理阶段分别维护系统提示词模板：

```text
asr_cleanup_prompt
ocr_cleanup_prompt
fusion_prompt
```

虽然三个阶段使用同一个文本模型，但提示词职责必须分开。

## ASR 清洗提示词要求

允许：

* 删除明显语气词；
* 修复标点；
* 修复断句；
* 合并被错误分割的句子；
* 保持时间顺序；
* 保留全部事实、论证、案例和细节。

禁止：

* 总结；
* 改写为教程；
* 删除重复论证，仅因为 AI 认为它不重要；
* 添加解释；
* 添加结论；
* 纠正讲者的事实观点；
* 改变立场。

## OCR 清洗提示词要求

允许：

* 按时间戳组织；
* 合并同一画面或连续画面中的重复识别；
* 去除明显播放器界面文字；
* 修复非常明确的 OCR 排版问题；
* 保留公式、标题、代码、表格文字和关键术语。

禁止：

* 依据常识补全无法辨认的内容；
* 解释图片；
* 生成图片摘要；
* 把多个不相关画面拼成一段；
* 删除原始时间戳。

## 融合提示词要求

必须明确写出：

```text
ASR 是主文稿。
OCR 是补充证据源。
只有在 ASR 缺失信息时才使用 OCR。
不要重复。
不要总结。
不要缩写。
不要补充视频外知识。
不要改变原作者观点。
```

所有提示词应放在独立文件或模板模块中，不要散落在业务代码里。

# 十一、数据目录结构

用户设置两个主要目录：

## 1. Obsidian 成品目录

例如：

```text
D:\Obsidian\MyVault\Video2Doc Inbox
```

这里直接存放最终 Markdown：

```text
Video2Doc Inbox/
├── 视频标题1.md
├── 视频标题2.md
└── 视频标题3.md
```

默认保持原视频标题作为文件名。

保存前需要自动清理 Windows 文件名非法字符：

```text
\ / : * ? " < > |
```

需要处理：

* 标题为空；
* 标题过长；
* 同名文件；
* 非法字符；
* 尾部句点或空格；
* Windows 保留文件名。

同名文件不要静默覆盖。

可以采用：

```text
标题.md
标题 (2).md
标题 (3).md
```

## 2. Video2Doc 资料目录

所有原始文件、中间产物、日志和处理记录放在独立数据目录中。

每个任务一个独立工作区。

建议结构：

```text
Video2Doc_Data/
└── YYYYMMDD_HHMMSS_安全化标题/
    ├── 00_source/
    │   ├── source.json
    │   ├── metadata.json
    │   ├── thumbnail.jpg
    │   └── media.ext
    │
    ├── 01_extract/
    │   ├── audio.wav
    │   └── frames/
    │
    ├── 02_asr/
    │   ├── raw.json
    │   ├── raw.srt
    │   ├── raw.txt
    │   └── cleaned.md
    │
    ├── 03_ocr/
    │   ├── raw.json
    │   ├── cleaned.md
    │   └── frames/
    │
    ├── 04_fusion/
    │   ├── input.json
    │   └── result.md
    │
    ├── 05_output/
    │   └── 视频标题.md
    │
    ├── task_config.json
    ├── task_state.json
    └── logs/
        └── task.log
```

如果 OCR 未启用：

* 可以不创建 `03_ocr`；
* 或创建目录并记录 `disabled`；
* 请选择一种一致方案，并写入架构文档。

工作区目录必须包含创建时间戳，方便用户以后按时间浏览和删除。

不要仅依赖文件修改时间。

# 十二、原始数据要求

必须分别保存以下层级。

## 1. ASR 原始结果

至少保存：

```text
raw.json
raw.srt
raw.txt
```

其中 JSON 是核心结构化数据。

每个片段建议包含：

```json
{
  "index": 1,
  "start": 12.5,
  "end": 18.2,
  "text": "原始转写内容"
}
```

还应记录：

* 模型名称；
* 语言；
* 执行时间；
* 可用时记录置信度；
* ASR 参数。

## 2. ASR 清洗结果

保存：

```text
02_asr/cleaned.md
```

不要覆盖原始转写。

## 3. OCR 原始结果

每条 OCR 结果至少包含：

```json
{
  "timestamp": 125.4,
  "frame_path": "frames/frame_000123.jpg",
  "text": "OCR 原始文字"
}
```

可以附加：

* 坐标框；
* OCR 置信度；
* 帧编号；
* 抽帧策略。

## 4. OCR 清洗结果

保存：

```text
03_ocr/cleaned.md
```

不要覆盖原始 OCR。

## 5. 融合结果

保存：

```text
04_fusion/result.md
```

## 6. 最终输出副本

在任务资料目录保存一份：

```text
05_output/标题.md
```

再将最终成品写入或复制到 Obsidian Inbox。

这样即使用户后来在 Obsidian 中修改或删除了文件，任务工作区仍保留生成时的原始输出。

# 十三、Markdown 输出规范

最终文件结构：

```markdown
---
title:
source_url:
source_type:
platform:
author:
channel:
published_date:
duration:
language:
created_at:
video2doc_version: v1.0

models:
  asr:
  ocr:
  text_processing:

providers:
  asr:
  ocr:
  text_processing:

processing:
  ocr_enabled:
  remove_fillers:
  timestamp_enabled:

  - video2doc

# 原视频标题

## 来源信息

视频链接：

原始网页链接：

平台：

作者或讲者：

频道或发布者：

发布时间：

视频时长：

## 视频简介

只有在来源中存在简介时才生成本节。

## 正文内容

正文……

---

## 原始资料

原始语音转写：

OCR 记录：

任务配置：
```

YAML 中 URL 必须作为独立属性保存，不能当作标签。

默认标签只包含：

```yaml
tags:
  - video2doc
```

不要自动生成主题标签。

`status` 默认可以为空，留给用户人工维护。

或者使用：

```yaml
status: generated
```

但软件不得擅自将它改成 `reviewed`。

## 时间戳

正文中的时间戳采用 HTML 注释：

```html
<!-- timestamp: 00:12:35 -->
```

这样 Obsidian 阅读模式不会显示，但程序未来可以解析。

不要在每一句后都插入时间戳。

建议在自然段、主题切换或合理时间间隔处保留时间戳。

原始 JSON 和 SRT 仍保存完整时间戳。

## OCR 内容

关键 OCR 内容可以自然融合进正文。

例如：

```markdown
讲者随后展示了注意力计算公式：

$$
\operatorname{Attention}(Q,K,V)
=
\operatorname{softmax}
\left(
\frac{QK^T}{\sqrt{d_k}}
\right)V
$$
```

不要在正文中写：

```text
OCR 识别结果：
```

完整 OCR 数据保留在资料目录。

正文底部可以提供原始资料路径。

由于最终 Markdown 位于 Obsidian Vault，而资料目录可能在 Vault 外部，应谨慎处理链接。

第一版可以：

* 写入纯文本绝对路径；
* 或写入 `file:///` 路径；
* 或只记录资料工作区路径。

不要假设 Obsidian 一定允许直接访问 Vault 外的相对路径。

请选择一种 Windows 和 Obsidian 下可用的实现，并在文档中说明。

# 十四、前端页面

第一版至少包含以下页面。

## 1. 首页 / 新建任务

功能：

* 输入一个或多个 URL；
* 拖入多个本地文件；
* 查看待添加输入；
* 选择处理方案；
* 选择是否启用 OCR；
* 展开高级设置；
* 加入队列。

## 2. 任务队列

展示：

* 当前处理中任务；
* 等待任务；
* 已完成任务；
* 失败任务；
* 已取消任务。

每个任务显示：

* 标题或输入名称；
* 输入类型；
* 状态；
* 当前阶段；
* 进度；
* 创建时间；
* 是否启用 OCR。

允许：

* 取消等待任务；
* 取消运行任务；
* 重试失败任务；
* 查看任务详情；
* 打开最终 Markdown；
* 打开成品所在文件夹；
* 打开资料工作区。

第一版可以不实现真正意义上的“暂停正在推理任务”。

不要提供一个实际上不能安全恢复的假暂停按钮。

可以支持：

* 取消；
* 停止队列继续启动下一项；
* 暂停队列调度。

但正在执行的单个外部命令是否能暂停，需要根据具体实现决定。

## 3. 任务详情

显示 Pipeline 阶段：

```text

下载或读取
音频提取
ASR
ASR 清洗
视频抽帧
OCR
OCR 清洗
内容融合
Markdown 生成
写入 Obsidian
```

未启用 OCR 时，OCR 阶段显示“未启用”，而不是显示失败。

显示：

* 阶段状态；
* 阶段耗时；
* 当前进度；
* 关键日志；
* 错误详情；
* 使用的配置快照；
* 输出文件路径。

## 4. 模型中心

功能：

* 手动添加模型；
* 编辑模型；
* 删除模型；
* 启用或停用模型；
* 设置能力标签；
* 添加备注。

不自动拉取 OneAPI 模型。

模型表单只要求：

```text
模型名称
能力标签
备注
是否启用
```

模型下拉列表按环节标签过滤。

ASR 下拉列表只显示带 `ASR` 标签的模型。

OCR 下拉列表只显示带 `OCR` 标签的模型。

文本处理下拉列表只显示带 `TEXT_PROCESSING` 标签的模型。

## 5. 模型组 / 处理方案

功能：

* 查看内置和自定义处理方案；
* 创建自定义处理方案；
* 复制处理方案；
* 编辑处理方案；
* 删除用户方案；
* 设置默认方案。

模型组保存完整工作流设置，不只是模型名称。

## 6. 设置

至少包含：

* OneAPI Base URL；
* OneAPI API Key；
* 测试 OneAPI 连接；
* Obsidian Vault 路径；
* Video2Doc Inbox 路径；
* Video2Doc 数据目录；
* FFmpeg 路径；
* yt-dlp 路径或运行方式；
* OCR 外部命令配置；
* 默认保留策略；
* 最后一次设置。

涉及路径时提供文件夹选择。

由于浏览器本身不能直接任意选择系统文件夹，本地 Web 软件需要由后台或桌面辅助能力实现路径选择。

可以先提供路径输入和后台验证，并在架构中预留原生文件夹选择方式。

# 十六、进程和取消机制

外部工具如 yt-dlp、FFmpeg、ASR 和 OCR 可能作为子进程运行。

需要设计统一的子进程管理器。

要求：

* 保存进程信息；
* 捕获 stdout；
* 捕获 stderr；
* 将重要输出写入任务日志；
* 支持取消任务；
* 取消时终止相关子进程；
* Windows 下考虑子进程树清理；
* 避免取消后遗留 FFmpeg 或 Python 子进程；
* 避免只停止前端状态而后台仍继续运行。

创建统一 ASR Provider 接口。

第一版可以优先实现 OneAPI 兼容 ASR 调用。

如果 OneAPI 的具体 ASR 请求格式无法完全统一，应将差异封装在 Provider 中，不要污染 Pipeline。

保存原始 JSON、SRT、TXT。

## 阶段 6：OCR

创建统一 OCR Provider 接口。

考虑两种接入能力：

```text
OneAPI OCR 模型
外部本地 OCR 命令
```

用户当前计划通过 OneAPI 管理模型，但原始 OCR 工具可能仍以本地命令形式运行，因此架构应允许外部 OCR 命令适配器。

第一版界面不必暴露复杂供应商概念，但后端需要允许不同执行适配器。

## 阶段 7：文本清洗和融合

实现：

* ASR 清洗；
* OCR 清洗；
* 融合；
* 提示词模板；
* OneAPI 文本模型调用；
* 长文本分块；
* 上下文连续性；
* 失败重试；
* 调用日志；
* Token 或成本信息在 API 可返回时记录。

长视频文本可能超过模型上下文长度。

必须设计可靠的分块方案。

分块不能造成：

* 内容丢失；
* 重复；
* 小标题大量重复；
* 前后文断裂；
* 时间戳错乱。

不要简单地按固定字符数切割并独立总结。

应该按 ASR 时间段、自然段或片段边界处理，并保存块之间的顺序。

OCR 融合也应优先根据时间戳匹配相关 ASR 区间，而不是把完整 OCR 文件无差别塞入每个分块。

## 阶段 8：Markdown 和 Obsidian

* 正文；
* 隐藏时间戳；
* 来源信息；
* 视频简介；

* 工作区副本；

## 阶段 9：错误处理和测试

补充：

* API 测试；
* 队列测试；

# 二十二、开发方式

请直接在仓库中开始工作。

先检查当前仓库状态。

如果仓库为空，则从零创建项目。

不要等待旧代码，因为不会提供旧代码。

不要假设存在任何历史实现。

开始时先创建：

```text
docs/PRODUCT_REQUIREMENTS.md
docs/ARCHITECTURE.md
docs/IMPLEMENTATION_PLAN.md
```

将本任务书中的确定需求整理进去。

然后开始实现。

工作过程中：

1. 每完成一个阶段，更新实施计划。
2. 保持项目始终可以启动。
3. 不提交无法运行的大量半成品代码。
4. 对重要架构决定写文档。
5. 优先完成真实可扩展的骨架，不要只制作静态页面截图。
6. 前端按钮不能只有外观，至少应连接真实 API 或明确显示尚未实现。
7. 不要用大量硬编码假数据掩盖缺失的后端设计。
8. 模拟 Pipeline 只用于验证队列，之后应能平滑替换为真实 Stage。
9. 不要擅自扩大产品范围。
10. 遇到次要歧义时，采用最简单且可扩展的合理方案，并记录决定。
11. 只有在缺少信息会导致无法继续或造成重大不可逆设计错误时，才向用户提问。
12. 不要反复询问已经在本任务书中确定的事项。

# 二十四、基础版本验收标准

以下行为应当可以实际验证：

1. 用户添加三个输入。
2. 系统创建三个任务。
3. 三个任务依次进入等待队列。
4. 第一个任务进入处理中。
5. 后两个任务保持等待。
6. 第一个任务完成后，第二个任务自动开始。
7. 刷新浏览器后状态不丢失。
8. 重启后台后已完成和等待任务仍然存在。
9. 用户可以添加名为 `whisper-large-v3` 的模型并标记为 ASR。
10. 用户可以添加名为 `paddleocr` 的模型并标记为 OCR。
11. 用户可以添加名为 `gpt-5-mini` 的模型并标记为 TEXT_PROCESSING。
12. 创建处理方案时，三个下拉列表只显示符合标签的模型。
13. 用户启用或关闭 OCR。
14. 新任务自动使用上一次实际使用的配置。
15. 修改本次任务配置不会自动覆盖处理方案。
16. 任务详情能显示配置快照。
17. 系统能创建带时间戳的数据工作区。
18. 模拟输出能生成符合规范的 Markdown。
19. 最终 Markdown 能写入配置的 Obsidian Inbox。
20. 资料文件不会混入 Obsidian Inbox。
21. 模拟任务失败时，前端能显示明确错误。
22. 用户可以重试失败任务。
23. 用户取消任务后，不会继续显示为处理中。
24. 日志中不出现 API Key。

# 二十五、最终提醒

Video2Doc 的核心不是“尽量让 AI 多做事”，而是：

```text
完整保留信息
降低视频学习的线性成本
保证来源可追溯
让用户自己完成理解和总结
```

任何功能设计和代码实现都必须服从这个目标。

不要把它逐渐改造成视频摘要工具。

不要默认加入任何知识提炼功能。

从零创建仓库，先完成架构文档和可运行基础版本，然后按照实施计划逐步接入真实处理能力。
